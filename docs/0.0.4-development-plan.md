# 0.0.4 开发计划：扫描式 UE 内建函数提示

## 目标

`0.0.4` 的核心目标是把 `UE.*` 内建函数提示改造成数据驱动。

在 Unreal 材质中，`UMaterialExpression` 的派生类可以声明材质图里的节点能力。DreamShader 可以把这些能力暴露为 `UE.TexCoord(...)`、`UE.Time()`、`UE.Expression(Class="...")` 等内建调用。当前 Rider 插件已经有基础的 `UE.*` 补全、签名帮助、悬浮文档，以及 `UE.Expression(Class="...")` 的 manifest fallback，但 `UE.*` 成员、签名和文档仍分散在多个硬编码表里。

本版本要建立一条清晰的扫描 / catalog 数据链，让新增 Unreal 材质表达式节点可以通过扫描或 manifest 自动进入补全，而不是每个节点都改 Kotlin 源码。

## 非目标

- 不重写 DreamShader parser。
- 第一版不做完整 C++ 语义解析。
- `0.0.4` 不把未知 `UE.*` 调用直接变成硬错误，避免误报。
- catalog 路径稳定前，不移除现有硬编码 fallback 数据。

## 当前基础

- 插件版本当前是 `0.0.3`，位置在 `gradle.properties`。
- `UE.*` 用法示例已在 `src/test/resources/upstream/Examples.md` 中覆盖。
- `DreamShaderMaterialExpressionManifest` 已经可以合并表达式类名来源：
  - 显式配置的 `materialExpressionManifestPath`
  - 项目 Bridge manifest
  - 插件 bundled fallback manifest
- `UE.Expression(Class="...")` 补全和诊断已经能消费 manifest 类名候选。
- `UE.*` 成员补全、签名帮助和悬浮文档仍分别维护硬编码表。

## 目标架构

引入一个统一的材质表达式 catalog，让所有编辑器功能共享同一份数据。

建议模型：

```kotlin
internal data class DreamShaderMaterialExpressionInfo(
    val className: String,
    val ueName: String,
    val signature: String?,
    val parameters: List<DreamShaderMaterialExpressionParameter>,
    val outputType: String?,
    val description: String?,
    val source: DreamShaderMaterialExpressionSource
)
```

建议职责：

- `DreamShaderMaterialExpressionCatalog`
  - 加载并合并 catalog entries。
  - 保持稳定的数据源优先级。
  - 提供兼容旧调用方的 `expressionClassNames()` helper。
- `DreamShaderMaterialExpressionManifest`
  - 同时解析旧 manifest 和新 manifest shape。
  - 将 manifest payload 转成 catalog entries。
- `DreamShaderMaterialExpressionScanner`
  - 对 Unreal C++ 材质表达式类做 best-effort 扫描。
  - 输出 catalog 兼容的数据。
- Editor consumers
  - completion、signature help、hover docs、diagnostics 都查询同一个 catalog，不再各自维护 `UE.*` 表。

## 数据源优先级

按以下顺序合并 catalog entries：

1. 显式配置的 manifest，也就是 `materialExpressionManifestPath`。
2. Bridge manifest：`Saved/DreamShader/Bridge/material-expression-manifest.json`。
3. 可选的 Unreal 源码扫描缓存。
4. 插件 bundled fallback manifest。
5. 迁移阶段保留的现有硬编码 built-ins fallback。

去重规则建议：先按标准化后的 `ueName` 去重，再按标准化后的 `className` 去重。

## Manifest 兼容设计

继续支持当前简单格式：

```json
{
  "classes": [
    { "className": "Sine" },
    { "name": "Multiply" }
  ]
}
```

新增更完整的格式，供扫描器或 Bridge 生成：

```json
{
  "expressions": [
    {
      "className": "UMaterialExpressionSine",
      "ueName": "Sine",
      "signature": "UE.Sine(Input=...)",
      "outputType": "float1",
      "description": "Creates a sine material expression.",
      "parameters": [
        {
          "name": "Input",
          "type": "float1",
          "required": false
        }
      ]
    }
  ]
}
```

fallback 规则：

- 如果缺少 `ueName`，从 `className` 派生。
- 如果 `className` 以 `UMaterialExpression` 开头，派生 `ueName` 时去掉这个前缀。
- 如果缺少 `signature`，展示 `UE.<ueName>(...)`。
- 如果缺少 `description`，生成一段中性的自动说明。

## 扫描器范围

第一版扫描器应该轻量、稳定、可降级：

- 扫描 Unreal Engine 源码根目录下的 `.h`，必要时再扩展到 `.cpp`。
- 识别这些形态：
  - `class UMaterialExpressionXxx : public UMaterialExpression`
  - 容易判断的 `UMaterialExpression` 子类的进一步派生类
- best-effort 提取 metadata：
  - 类名
  - `UCLASS` / `DisplayName` 中的展示名
  - 容易识别的 input-like `UPROPERTY` 名称
  - 类附近注释作为可选 description
- 跳过 generated / intermediate 目录。
- 不允许长时间扫描阻塞 editor completion。

扫描器可以输出不完整 entry。只要能稳定得到 `ueName`，对补全就已经有价值。

## 设置与缓存

catalog parser 稳定后，可以考虑新增项目设置：

- `unrealEngineSourceRoot`
- `materialExpressionScanEnabled`
- `materialExpressionScanCachePath`

缓存策略：

- 扫描结果保存为 manifest 兼容 JSON。
- completion、signature help、hover docs 使用缓存，不实时扫源码。
- 以下情况触发失效：
  - Unreal source root 变化
  - cache format version 变化
  - plugin version 变化
  - 扫描输入文件时间戳变化
  - 用户手动刷新

## 实施阶段

### Phase 1：版本与文档

- 开始实现时将项目版本提升到 `0.0.4`。
- changelog 记录扫描式 / catalog-based `UE.*` 补全。
- README 保留本计划入口。

### Phase 2：Catalog 模型

- 新增 catalog entry 和 parameter data class。
- 重构 manifest parser，让它返回 rich entries。
- 保留 `expressionClassNames()`，兼容现有调用方。
- 增加旧 manifest shape 和新 manifest shape 的 parser 测试。

### Phase 3：补全集成

- `UE.` 成员补全改为从 catalog 读取。
- 保留现有硬编码 `UE.*` built-ins 作为 fallback。
- `UE.Expression(Class="...")` 的 class value 补全也改为从同一个 catalog 读取。
- 增加测试：只存在于 manifest/catalog 的节点可以出现在 `UE.` 补全中。

### Phase 4：签名帮助集成

- `UE.<Name>(...)` 签名从 catalog 解析。
- catalog 信息不完整时回退到现有签名表。
- 增加 catalog-provided signature 测试。

### Phase 5：悬浮文档集成

- `UE.*` hover docs 从 catalog 解析。
- 保留用户 hover documentation overrides 的优先级。
- 增加 catalog docs 与 override priority 测试。

### Phase 6：扫描器原型

- 实现 best-effort 文本扫描器，识别 `UMaterialExpression` 派生类。
- 输出 manifest-compatible cache JSON。
- 用小型 synthetic Unreal header fixtures 写扫描器测试。

### Phase 7：诊断加固

- 保留现有 `UE.Expression(Class="...")` unknown-class validation。
- suggestion 候选改为 catalog-derived class names。
- 暂不引入大范围 unknown `UE.*` 诊断，等扫描覆盖率稳定后再考虑。

### Phase 8：发布前验证

- 运行 completion、documentation、diagnostics、performance 相关测试。
- 验证以下 fallback 场景：
  - 无 manifest
  - 显式 manifest path 无效
  - 旧 manifest shape
  - 新 manifest shape
  - scanned cache
- 实现完成后更新 README coverage notes。

## 验收标准

- `UE.` 补全可以展示并非 Kotlin 硬编码的 entry。
- `UE.Expression(Class="...")` 和 `UE.<Name>(...)` 共用同一个 catalog。
- 旧 manifest 文件继续可用。
- scan / manifest 数据缺失或无效时，可以降级到 bundled fallback。
- signature help 和 hover docs 能在有 catalog 数据时使用 catalog。
- 测试覆盖 manifest 兼容性，以及至少一个 catalog-only completion entry。

## 风险

- Unreal 的 `UMaterialExpression` metadata 不一定足够推导完整 DreamShader 调用签名。
- 不同 UE 版本的类名、metadata 和路径可能不同。
- 在 JetBrains 插件里引入完整 C++ parser 成本较高，不适合作为第一版路径。
- Bridge 生成的 manifest 可能比插件直接扫描源码更可靠；如果存在 Bridge 数据，应优先使用。

## 推荐的第一步实现切片

先做 catalog 与 manifest 兼容层，再把它接入 `UE.` 补全。这一步能最快带来用户可见收益，也能为后续 signature help、hover docs 和源码扫描打好基础。
