## 目标

`0.0.4` 的核心目标是把 `UE.*` 内建函数提示改造成数据驱动。

在 Unreal 材质中，`UMaterialExpression` 的派生类可以声明材质图里的节点能力。DreamShader 可以把这些能力暴露为 `UE.TexCoord(...)`、`UE.Time()`、`UE.Expression(Class="...")` 等内建调用。当前 Rider 插件已经有基础的 `UE.*` 补全、签名帮助、悬浮文档，以及 `UE.Expression(Class="...")` 的 manifest fallback，但 `UE.*` 成员、签名和文档仍分散在多个硬编码表里。

本版本要建立一条清晰的扫描 / catalog 数据链，让新增 Unreal 材质表达式节点可以通过扫描或 manifest 自动进入补全，而不是每个节点都改 Kotlin 源码。

## 非目标

- 不重写 DreamShader parser。
- 第一版不做完整 C++ 语义解析。
- `0.0.4` 不把未知 `UE.*` 调用直接变成硬错误，避免误报。
- catalog 路径稳定前，不移除现有硬编码 fallback 数据。

## 当前基础

- 插件版本当前是 `0.0.3`，位置在 `gradle.properties`。
- `UE.*` 用法示例已在 `src/test/resources/upstream/Examples.md` 中覆盖。
- `DreamShaderMaterialExpressionManifest` 已经可以合并表达式类名来源：
  - 显式配置的 `materialExpressionManifestPath`
  - 项目 Bridge manifest
  - 插件 bundled fallback manifest
- `UE.Expression(Class="...")` 补全和诊断已经能消费 manifest 类名候选。
- `UE.*` 成员补全、签名帮助和悬浮文档仍分别维护硬编码表。

## 目标架构

引入一个统一的材质表达式 catalog，让所有编辑器功能共享同一份数据。

建议模型：

```kotlin
internal data class DreamShaderMaterialExpressionInfo(
    val namespace: String,
    val className: String,
    val ueName: String,
    val signature: String?,
    val parameters: List<DreamShaderMaterialExpressionParameter>,
    val outputType: String?,
    val description: String?,
    val source: DreamShaderMaterialExpressionSource
)
```

建议职责：

- `DreamShaderMaterialExpressionCatalog`
  - 加载并合并 catalog entries。
  - 保持稳定的数据源优先级。
  - 提供兼容旧调用方的 `expressionClassNames()` helper。
  - 支持 `namespace + member` 查询，默认 namespace 为 `UE`，为 `Substrate.*` 等 wrapper 预留同一条数据路径。
- `DreamShaderMaterialExpressionManifest`
  - 同时解析旧 manifest 和新 manifest shape。
  - 将 manifest payload 转成 catalog entries。
- `DreamShaderMaterialExpressionScanner`
  - 对 Unreal C++ 材质表达式类做 best-effort 扫描。
  - 输出 catalog 兼容的数据。
- Editor consumers
  - completion、signature help、hover docs、diagnostics 都查询同一个 catalog，不再各自维护 `UE.*` 表。

## 数据源优先级

按以下顺序合并 catalog entries：

1. 显式配置的 manifest，也就是 `materialExpressionManifestPath`。
2. Bridge manifest：`Saved/DreamShader/Bridge/material-expression-manifest.json`。
3. 可选的 Unreal 源码扫描缓存。
4. 插件 bundled fallback manifest。
5. 迁移阶段保留的现有硬编码 built-ins fallback。

去重规则建议：先按标准化后的 `ueName` 去重，再按标准化后的 `className` 去重。

## Manifest 兼容设计

继续支持当前简单格式：

```json
{
  "classes": [
    { "className": "Sine" },
    { "name": "Multiply" }
  ]
}
```

新增更完整的格式，供扫描器或 Bridge 生成：

```json
{
  "expressions": [
    {
      "namespace": "UE",
      "className": "UMaterialExpressionSine",
      "ueName": "Sine",
      "signature": "UE.Sine(Input=...)",
      "outputType": "float1",
      "description": "Creates a sine material expression.",
      "parameters": [
        {
          "name": "Input",
          "type": "float1",
          "required": false
        }
      ]
    }
  ]
}
```

fallback 规则：

- 如果缺少 `namespace`，默认使用 `UE`。
- 如果缺少 `ueName`，从 `className` 派生。
- 如果 `className` 以 `UMaterialExpression` 开头，派生 `ueName` 时去掉这个前缀。
- 如果缺少 `signature`，展示 `UE.<ueName>(...)`。
- 如果缺少 `description`，生成一段中性的自动说明。

## 扫描器范围

第一版扫描器应该轻量、稳定、可降级：

- 扫描 Unreal Engine 源码根目录下的 `.h`，必要时再扩展到 `.cpp`。
- 识别这些形态：
  - `class UMaterialExpressionXxx : public UMaterialExpression`
  - 容易判断的 `UMaterialExpression` 子类的进一步派生类
- best-effort 提取 metadata：
  - 类名
  - `UCLASS` / `DisplayName` 中的展示名
  - 容易识别的 input-like `UPROPERTY` 名称
  - 类附近注释作为可选 description
- 跳过 generated / intermediate 目录。
- 不允许长时间扫描阻塞 editor completion。

扫描器可以输出不完整 entry。只要能稳定得到 `ueName`，对补全就已经有价值。

## 设置与缓存

catalog parser 稳定后，可以考虑新增项目设置：

- `unrealEngineSourceRoot`
- `materialExpressionScanEnabled`
- `materialExpressionScanCachePath`

自动检测 `unrealEngineSourceRoot`（已实现）：

- 引擎既可能是 GitHub 源码版，也可能是 Launcher 发行版里额外下载了引擎源码的安装，两者都带 `Engine/Source`，因此探测不依赖目录命名约定，而是顺着工程文件指向的引擎位置走。
- `DreamShaderUnrealSourceLocator` 探测链：
  1. `.sln`：Unreal 生成的解决方案以相对路径引用引擎目录（如 `..\UnrealEngine\UntoonEngine\Engine\...`），取最高频的 `...\Engine\` 前缀去掉末尾 `Engine` 得引擎根，相对 sln 目录解析为绝对路径，并校验 `Engine/Source` 存在。
  2. `.uproject` 回退：读 `EngineAssociation`，GUID 形态查 `HKCU\Software\Epic Games\Unreal Engine\Builds`（自定义 / 源码引擎），版本号形态查 `HKLM\SOFTWARE\EpicGames\Unreal Engine\<ver>\InstalledDirectory`（Launcher 发行版）。注册表用系统 `reg query` 读取（JVM 无原生注册表 API），非 Windows / 失败静默跳过。
- 候选填入最窄的有效扫描目录：优先 `Engine/Source/Runtime/Engine/Classes/Materials`，其次 `.../Public/Materials`（UE 版本 / 模块拆分差异），两者都没有才回退 `Engine/Source`；版本来自 `Build.version` 或 Launcher 版本号。
- 设置 UI 在该字段旁加"自动检测"按钮：无候选时提示手填、单候选直接填、多候选弹选择框；全程 best-effort，读盘 / 起子进程失败静默回退。

缓存策略：

- 扫描结果保存为 manifest 兼容 JSON。
- completion、signature help、hover docs 使用缓存，不实时扫源码。
- 以下情况触发失效：
  - Unreal source root 变化
  - cache format version 变化
  - plugin version 变化
  - 扫描输入文件时间戳变化
  - 用户手动刷新

### Phase 6：扫描器原型 ✅

- 实现 best-effort 文本扫描器，识别 `UMaterialExpression` 派生类。
- 输出 manifest-compatible cache JSON。
- 用小型 synthetic Unreal header fixtures 写扫描器测试。

实现要点：
- `DreamShaderMaterialExpressionScanner` 以 `UCLASS(...)` 为锚，配对随后的 `class U... : public U...` 声明，只认 `UMaterialExpression*` 类名或基类。
- best-effort 提取 metadata：`meta=(DisplayName="...")` 作为 `ueName`、`FExpressionInput` 等 input-like `UPROPERTY` 作为 parameters、紧邻 `UCLASS` 的 `/** */` 注释作为 description。
- `scanDirectory` 跳过 `intermediate` / `generated` / `binaries` / `saved` 目录，单文件读取失败时跳过而非中断。
- `toManifestJson` 输出的就是 catalog 已消费的 rich manifest shape，扫描结果与 Bridge / bundled manifest 走同一条解析路径（round-trip 测试覆盖）。
- catalog 合并把 scanned cache 放在 Bridge manifest 之后、bundled fallback 之前（数据源优先级第 3 位）；优先读 `materialExpressionScanCachePath`，仅当启用扫描且无缓存时才实时扫 `unrealEngineSourceRoot`。
- 与计划"设置与缓存"一节对应，新增项目设置 `unrealEngineSourceRoot`、`materialExpressionScanEnabled`、`materialExpressionScanCachePath`，并接入设置 UI。

设计说明（UHT / 反射）：Unreal 的反射数据（`UCLASS`/`UPROPERTY`/`meta`）在编辑器运行时最完整，对应本计划的 Bridge manifest 路径，应优先使用。插件端 `.h` 文本扫描器不复刻 UHT，只作为没有 Bridge、无法跑编辑器时的兜底，能稳定得到 `ueName` 即有价值。

### Phase 7：诊断加固 ✅

- 保留现有 `UE.Expression(Class="...")` unknown-class validation。
- suggestion 候选改为 catalog-derived class names。
- 暂不引入大范围 unknown `UE.*` 诊断，等扫描覆盖率稳定后再考虑。
- 加入 Substrate 边界诊断候选：`Base.FrontMaterial` / `Base.MaterialAttributes` 互斥、`Substrate` 不参与普通数值运算 / swizzle / `if` 分支合并、`UMaterialExpressionCustom` 不允许 `OutputType="Substrate"`。
- 同步上游 Layer shape 规则：`ShaderLayer` 最多一个 `MaterialAttributes` 输入；`ShaderLayerBlend` 必须刚好两个 `MaterialAttributes` 输入。

实现要点：
- `Base.FrontMaterial` 现已纳入 `BASE_OUTPUT_MEMBERS` 已知成员，不再被误报为未知输出。它是 Substrate 的绑定目标。
- 新增 `annotateSubstrateBindingExclusivityDiagnostics`：按声明扫描 `outputs` / `graph` section，仅以赋值锚点（`Base.X =`）识别绑定目标，若同一声明同时绑定 `Base.FrontMaterial` 与 `Base.MaterialAttributes`，在两处目标各报一次 `diagnostic.frontMaterialMaterialAttributesExclusive`。
- `annotateLayerRules` 收紧：`ShaderLayerBlend` 必须刚好两个输入且都为 `MaterialAttributes`（原先只校验"至少两个 MA"）；`ShaderLayer` 最多一个输入且若存在必须为 `MaterialAttributes`，对应新消息 `diagnostic.layerRequiresMaterialAttributesInput`。
- `annotateUnknownExpressionClassDiagnostics` 增加分支：`OutputType="Substrate"` 且 `Class` 归一化后为 `Custom`（接受 `Custom` / `MaterialExpressionCustom` / `UMaterialExpressionCustom`）时报 `diagnostic.customExpressionDisallowsSubstrateOutput`。`Substrate` 本身已是合法 lexer 类型，故仅 Custom 组合被拒。
- 测试：`DreamShaderSectionShapeDiagnosticsTest` 新增 layer 输入 shape 用例；`DreamShaderSemanticDiagnosticsTest` 新增 FrontMaterial 识别、FrontMaterial/MaterialAttributes 互斥、Custom+Substrate 拒绝用例。

延后项（保持 0.0.4 非目标"避免误报"）：`Substrate` 参与算术 / swizzle / `if` 分支合并的语义诊断需要表达式级类型推导，当前 pipeline 为 best-effort 文本扫描，强行加会产生误报，留待表达式语义层成熟后再做。

## 验收标准

- `UE.` 补全可以展示并非 Kotlin 硬编码的 entry。
- `UE.Expression(Class="...")` 和 `UE.<Name>(...)` 共用同一个 catalog。
- 旧 manifest 文件继续可用。
- scan / manifest 数据缺失或无效时，可以降级到 bundled fallback。
- signature help 和 hover docs 能在有 catalog 数据时使用 catalog。
- 测试覆盖 manifest 兼容性，以及至少一个 catalog-only completion entry。

## 风险

- Unreal 的 `UMaterialExpression` metadata 不一定足够推导完整 DreamShader 调用签名。
- 不同 UE 版本的类名、metadata 和路径可能不同。
- 在 JetBrains 插件里引入完整 C++ parser 成本较高，不适合作为第一版路径。
- Bridge 生成的 manifest 可能比插件直接扫描源码更可靠；如果存在 Bridge 数据，应优先使用。

## 推荐的第一步实现切片

先做 catalog 与 manifest 兼容层，再把它接入 `UE.` 补全。这一步能最快带来用户可见收益，也能为后续 signature help、hover docs 和源码扫描打好基础。
